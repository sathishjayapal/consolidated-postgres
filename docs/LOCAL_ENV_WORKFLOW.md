# Local Environment Workflow & Guardrails

This document describes the canonical way to start the local development databases/broker, verify architectural guardrails, and toggle between local and cloud infrastructure without violating security requirements.

## Directory Layout

```
consolidated-postgres/
├── docs/
│   └── LOCAL_ENV_WORKFLOW.md   # You are here
├── scripts/
│   ├── lib/
│   │   └── project-config.sh   # Shared metadata for projects (ports, env keys, etc.)
│   └── local/
│       ├── multi-dev-up.sh     # Start Postgres containers + RabbitMQ (local/cloud aware)
│       ├── multi-dev-down.sh   # Stop Postgres containers, optional volume wipe
│       └── multi-dev-verify.sh # Guardrail verification script
├── compose/rabbitmq-compose.yml        # Local RabbitMQ definition used by multi-dev-up
└── START_HERE.md               # Cloud environment bootstrap instructions
```

## Prerequisites

1. Docker Desktop running and logged in (for local containers).
2. `eventstracker` and `runs-app` repositories checked out as siblings of `consolidated-postgres`.
3. Each project has its own `dev-up.sh` script (already present) capable of generating a `.env` file with database credentials.

## Local Startup

```bash
cd consolidated-postgres
scripts/local/multi-dev-up.sh
```

What happens:
1. Starts/ensures RabbitMQ via `compose/rabbitmq-compose.yml`.
2. Invokes each project’s `dev-up.sh` to start its dedicated Postgres container.
3. Reads passwords from `eventstracker/.env` and `runs-app/.env` (created by the per-project scripts) instead of hard-coding them.
4. Verifies connectivity, Flyway migrations, and seed data when running in local mode.

> **Security Guardrail:** No credentials are embedded in the orchestrator; they are resolved from `.env` files produced by the individual projects or from environment overrides (`EVENTSTRACKER_DB_PASSWORD`, `RUNS_APP_DB_PASSWORD`).

### Reset Local Databases

```bash
scripts/local/multi-dev-up.sh --reset
```

Resets both containers by calling each project’s `dev-up.sh --reset` before the normal startup flow. The reset is skipped automatically in `--cloud` mode.

## Guardrail Verification

After startup—or inside CI for a pre-flight check—run:

```bash
scripts/local/multi-dev-verify.sh
```

Checks performed:
- All service-specific Postgres containers and RabbitMQ are running.
- Ports `5432` (EventTracker) and `5443` (Runs App) respond using credentials sourced from the `.env` files or environment variables.
- Flyway seed tables exist and contain data (`domain`, `run_app_user`).
- Spring configuration files still point to the mandated local ports and reference externalized password properties.
- Each service’s frontend must be started (`npm run devserver` or equivalent) and exercised for a quick smoke test to confirm TypeScript compilation and runtime errors are absent before changes are considered complete.

### Cloud Mode Verification

When developing against the DigitalOcean databases:

```bash
scripts/local/multi-dev-verify.sh --cloud
```

The script skips container and seed checks (since they belong to cloud infrastructure) but still validates Spring configuration guardrails.

## Cloud Database Toggle

Both `eventstracker/dev-up.sh` and `runs-app/dev-up.sh` support a `--cloud` flag that reads the connection details from `env/.env.cloud` (generated by `scripts/cloud/cloud-start.sh`). The orchestrator forwards `--cloud` when invoked as:

```bash
scripts/local/multi-dev-up.sh --cloud
```

Behavior in cloud mode:
- Local containers are not started (RabbitMQ is skipped; `--reset` is ignored).
- The orchestrator invokes each project’s `dev-up.sh --cloud`, which writes cloud-specific `.env` files only—no Docker interaction.
- Guardrail script `multi-dev-verify.sh --cloud` skips local DB checks to avoid leaking credentials or attempting to connect to remote infrastructure without explicit configuration.

## Shutdown

```bash
scripts/local/multi-dev-down.sh          # stop containers but retain data
scripts/local/multi-dev-down.sh --volumes # stop and delete volumes
```

## Environment Overrides

Set or export the following variables to avoid reading from repo-local `.env` files (useful in CI or when rotating credentials):

- `EVENTSTRACKER_DB_PASSWORD`
- `RUNS_APP_DB_PASSWORD`

`multi-dev-up.sh` and `multi-dev-verify.sh` will use these overrides automatically.

## CI / Pre-flight Integration

- `scripts/local/multi-dev-up.sh` can be invoked in CI to bring up local Postgres containers using ephemeral runners. Provide the required `.env` files or export password environment variables beforehand.
- Run `scripts/local/multi-dev-verify.sh` as part of gating checks to ensure the architecture rules (separate databases, RabbitMQ availability, seed data) remain intact.
- For cloud-oriented pipelines, use `--cloud` on both scripts to generate `.env` files and perform configuration checks without starting local containers.

## IntelliJ Services Parallel Setup

To align with the IntelliJ **Services** tool window (Run → Services):

1. Create Run Configurations for each long-running process.
   - *Shell Script* configuration: `scripts/local/multi-dev-up.sh` (working directory = repo root).
   - *Spring Boot* configurations for each backend (`mvn spring-boot:run`).
   - *NPM* configurations for each frontend (`npm run devserver` or equivalent).
2. Define a **Compound** configuration that starts all required entries together. Pin it to the Services window so a single click launches every backend and frontend in parallel.
3. Add another configuration for `scripts/local/multi-dev-verify.sh` (or `--cloud`) to execute guardrail checks once the services are up.
4. Keep the Services window open to monitor logs, restart individual components, or stop everything as a group when smoke tests and guardrails finish.

## Troubleshooting

- **Missing password error:** Run the corresponding project’s `dev-up.sh` locally to regenerate `.env`, or provide the environment variable override.
- **RabbitMQ health warning:** Ensure Docker has access to port `5672` and the container is not already allocated to another project.
- **Schema not applied:** Start the Spring Boot applications (`mvn spring-boot:run`) so Flyway can execute and seed data; then rerun `scripts/local/multi-dev-verify.sh`.

With this workflow, local development remains idempotent, credentials stay out of the repository, and the architecture guardrails are enforced with a single command.
